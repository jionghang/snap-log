# SnapLog

Windows 桌面小工具：跟随前台窗口切换（或按固定间隔）截图 → 本机 OCR 出文字 → 连同截图一起存进本机 SQLite → 按需或定时调用大模型生成活动总结 → 按需或定时把大模型生成的总结写进飞书多维表格。内置带筛选、分页、详情、导出 CSV 的记录查看器。

- **OCR 用离线 PaddleOCR（PP-OCRv6 tiny）**，中文准确率实测是系统内置 OCR 的约 2.4 倍；支持**实时识别**或**每天定时批量识别**（把耗 CPU 的活儿挪到机器空闲时段）。
- **大模型支持配置多个**，依次回退 + 指数退避重试；可只发文字、只发截图、或文字 + 截图（同窗口按时间采样，避免重复发同一画面）。
- **可维护自己的工作项目清单**，让总结按项目归类。
- **可把大模型总结写进飞书多维表格**（自建应用 + tenant_access_token，不需要用户授权；生成后自动 / 定时 / 手动三种触发）。
- 全程离线，默认不联网。

## 快速开始

### 环境要求

- **Windows 10 1809+ / Windows 11，64 位**（PaddleOCR 原生推理库只有 win-x64）
- 构建需要 **.NET SDK**（目标框架 `net10.0-windows10.0.19041.0`）
- **磁盘约 460MB**（PaddleOCR 原生库约 330MB + 模型约 90MB）；截图另占空间
- 想用备用引擎还需要系统中装了**中文 OCR 语言包**

> 本机已把 .NET 10 SDK 装到 `%USERPROFILE%\.dotnet`（用户目录，免管理员，删目录即可还原）。
> 因为没注册到系统，命令行用 `dotnet` 前需要：
> ```
> setx PATH "%PATH%;%USERPROFILE%\.dotnet"
> ```
> 或直接 `publish.cmd` 出自包含版本（不需要 .NET 环境）。

### 构建与运行

```cmd
build.cmd            :: 开发版
publish.cmd          :: 自包含版（约 600MB）

run.cmd --selftest   :: 全链路自检
run.cmd --ui-smoke   :: 界面自检
run.cmd              :: 启动托盘应用
```

## 界面

三个窗口，都从托盘图标（双击打开主窗口）或托盘右键菜单进入。

### 主窗口（八个标签页）

| 标签页 | 内容 |
|---|---|
| **状态** | 运行状态（启动中/运行中/已暂停）、本次运行抓取条数、最近一次抓取、总共抓取、**开机自启动**开关、实时运行日志。按钮：暂停/开始记录、立即抓取一次 |
| **抓取记录** | 记录查看器：筛选（时间/进程/状态/关键词）、分页、详情、打开截图、导出 CSV、**多选删除**（二次确认，可勾选同时删除截图文件） |
| **总结记录** | 总结历史：成功和失败都记，含触发来源、覆盖范围（哪一天）、模型、尝试次数、耗时；工具条上有**刷新 / 现在生成一次 / 生成范围（可只总结指定日期）/ 删除（多选，可连 .txt 文件一起删）**，详情标题旁是**打开总结文件 / 打开总结目录** |
| **抓取配置** | 延时截图时长、抓取周期、保存截图、截图目录、截图与记录保留天数 |
| **OCR 配置** | 引擎、模型、MKLDNN、CPU 线程数、识别方式（实时/每天定时）、**测试识别** |
| **大模型配置** | 启用、模型列表、发送内容、图片选项、失败重试、定时生成、系统提示词（含“恢复默认模板”）、工作项目 |
| **推送配置** | 飞书多维表格：写入开关、生成后自动写入、定时写入、写入范围、应用凭证、app_token / table_id、字段映射（可增删）、**测试连接**、**读取表字段名**、**立即写入** |
| **关于** | 软件说明、版本/运行时/系统、许可证（MIT）、项目地址（可一键打开），以及数据/日志/总结/截图四个目录的入口 |

> **为什么拆成八页**：原来是一个“设置”标签页里堆了一百六十多个控件，要往下拖很久才能找到想改的东西。
> 现在按用途分成四页配置，每页只有自己那一类。

关闭主窗口只是收起，进程继续在托盘里记录；退出走托盘菜单。

性能上也做了处理（原本设置页点开会卡一下）：

- **懒加载**：主窗口打开时只建状态页和两张记录页，四张配置页和关于页先放占位；配置页第一次被点开时才建，之后就一直在。
- **空闲预建**：程序启动后趁空闲（用户没在操作的空隙）把占位页都建好，所以你点开设置页时它通常已经在那里了。
- **挂起布局**：每个设置页构建时 `SuspendLayout`，避免每加一个控件就重排一遍。

实测：主窗口构造约 **95 ms**（改之前一次性建全部是 ~490 ms），各配置页单独构建 50~190 ms 且只付一次。

### 托盘菜单

只留三件事：**运行状态（点击暂停/继续）**、**显示主窗口**、**退出**。

其余操作都在主窗口的页签里（抓取、记录、总结、设置、推送），不在这里重复一遍——菜单短一点，误点少一点。双击托盘图标也能打开主窗口。

### 各配置页内容

**抓取配置**

- **延时截图时长**（毫秒，默认 5000）
- **抓取周期**（分钟，默认 10）
- 保存截图、截图目录（可浏览/打开）
- 截图保留天数、记录保留天数

**OCR 配置**

- 引擎：PaddleOCR / 系统内置 Windows OCR / 关闭
- 模型：v6 tiny（推荐）/ v6 small / v5 mobile
- 启用 MKLDNN（快 3~4 倍，内存 145MB → 640MB）、CPU 线程数
- **识别方式**：实时识别 / 每天定时批量识别 + 时间
- **测试识别**：抓一次当前窗口走一遍真实识别链路，**弹出结果预览**（左图右文）——光说"识别成功"没用，你要确认的是"这段字认得对不对"
- 下方实时显示引擎状态；选 PaddleOCR 时不会为了显示状态就去加载它

**大模型配置**

- 启用开关
- **模型列表**（增删改、上移下移、启用/停用，双击编辑）
- 发送内容（只文字 / 文字+截图 / 只截图）、图片选项（同窗口间隔、最多张数、清晰度）
- 失败重试（次数 + 起始间隔）
- **定时生成**（开关 + 时间）
- **系统提示词**（编辑 / 显示当前是默认模板还是已自定义）
- **工作项目**（增删改、上移下移，双击编辑）
- **总结历史**入口

**推送配置**

定时推送开关与时间、应用凭证（App ID / App Secret）、数据表（app_token / table_id）、字段映射、**测试连接**、**立即写入…**


### 模型配置对话框

编辑模型列表里的一项。**边填边提示**：补齐 `/v1` 后实际会被请求的地址、密钥来源、是否与已有配置重复、要用图片时的视觉能力提醒。

底部有“**测试连接**”：用当前填的内容**真实调一次模型**（很小的请求），验证地址、密钥、模型名三件事都对得上。失败时把每个模型的失败明细列出来。这是唯一能确认配置可用的办法。

拿不到密钥时不允许保存。

### 记录查看器

筛选（时间范围 / 进程 / 状态 / 关键词）、分页（50~1000 条/页）、详情（含**窗口标题、窗口类名、截图路径与是否存在**、提示/错误、完整识别文字）、**打开截图**、导出 CSV（当前筛选下的全部结果）、打开截图目录。快捷键 `F5` / `Ctrl+PageUp/PageDown` / `Esc`。

详情标题旁的“打开截图 / 打开截图目录”与总结记录页的“打开总结文件 / 打开总结目录”是同一套布局，两页操作方式保持一致。

**批量删除**：按住 Ctrl / Shift 多选后点“删除”，会先弹二次确认，并可以勾选**同时删除对应的截图文件**——默认不勾：删记录是常规操作，删文件不可撤销。

> 状态列会出现 **`Pending`**：识别方式是"每天定时"时的正常中间态，批次跑完会变成 Ok/NoText/Error。

### 总结历史

时间、触发来源（手动/定时/命令行）、结果、模型、记录数/图数、耗时、内容摘要。**成功和失败都记**——定时任务半夜失败了第二天得能查到原因。下方是完整总结正文或失败明细。

正文直接存在库里，所以历史查看不依赖文本文件还在不在。

## OCR 引擎

### 为什么用 PaddleOCR

同一张真实截图（1650×925 的中文网页 + 浏览器工具栏 + 侧边栏）、同一套 24 个对照词组：

| 引擎 | 命中率 | 耗时 | 私有内存 |
|---|---|---|---|
| 系统内置 Windows OCR | **9 / 24**（37%） | 232 ms | ~56 MB |
| **PaddleOCR PP-OCRv6 tiny** | **22 / 24**（92%） | 1268 ms | 见下 |

差距集中在**小字号中文**（浏览器标签、书签栏）和**长句**。同一窗口的另一个对比：系统 OCR 给 110 行，PaddleOCR 给 37 行——它按语义行聚合，而不是把中文逐字拆开，对后续总结更有利。

### 只服务中文，所以不做语言配置

随包发布的是中文模型（PP-OCRv5 mobile、PP-OCRv6 tiny/small）。这个工具只服务中文场景，因此**没有语言下拉框**，也**不开放自定义模型目录**——要挂别的模型就在 `PaddleModelKind` 加一个枚举值。备用引擎（系统 OCR）也不再暴露语言设置，直接用系统首选语言。

### MKLDNN：速度与内存的权衡

实测（1650×925 截图，2×2 分块，4 线程），**准确率完全一致**（都是 22/24）：

| MKLDNN | 首次识别 | 稳定态单块 | 稳定态私有内存 |
|---|---|---|---|
| **关（默认）** | 3965 ms | 1310 ms | **145 MB** |
| 开 | 1378 ms | 337 ms | 643 MB |

默认关掉：省约 500MB 内存，代价是一张全屏截图约 4~6 秒。如果改成"每天定时识别"，这段耗时完全可以接受。

### 延迟加载

引擎在**首次需要识别时**才初始化（约 400ms、约 100MB）。界面上显示 `· 未加载` / `· 已加载`。

实测内存（MKLDNN 关闭）：加载后约 98MB → 识别后约 130MB → **`Dispose()` 后回落到约 92MB**。推理用的那部分能释放，原生 DLL 已映射的约 90MB 要等进程退出（`GC.Collect` 和 `EmptyWorkingSet` 都实测无效）。所以**没做"空闲自动卸载"**：只省约 38MB，却要付约 400ms 重新加载。

### 免费社区版的硬限制

PaddleOCRSharp 免费社区版**限制单次调用检测到的文本框数必须小于 100**。密集界面整屏轻松超过，会抛
`The free community edition only support box sizes <100`。

引擎做**自适应分块**：整图试一次 → 撞限制就拆 2×2 递归（最多 4×4）→ 每个文本块带坐标返回，**按位置合并回正确阅读顺序**（跨块被切断的行会重新拼成一行）。抓一张 1650×925 网页面板通常走 4 块。

某块拆到最深仍超限会被跳过——这时**不会静默丢数据**：提示会写进日志（Warn 级）和记录的“错误”列。想彻底去掉限制需要商业授权（原生库提供 `AddLicense`）。

## 识别时机：实时 vs 每天定时

| 方式 | 行为 | 适合 |
|---|---|---|
| **实时识别**（默认） | 抓到就识别，结果马上能用 | 想让记录立刻可查 |
| **每天定时批量识别** | 白天只截图，到设定时间（默认 02:00）统一补识别 | 机器性能一般，或者想让 CPU 只在你不用电脑时空转 |

定时模式下的几个设计：

- 记录先以 **`Pending`** 状态落库（有截图、没文字），批次跑完变成 Ok / NoText / Error。
- **强制保存截图**：没图就没法事后识别。定时模式下“保存截图”会被锁成开启，避免配出跑不通的组合。
- **失败也会落地**：截图文件不在了（被保留策略清了、或手动删了）会记成 `Error` 并注明原因，而不是永远挂在 Pending 上每轮重试。
- **按时间升序处理**，积压时优先补上最早的历史；单批最多 2000 条，剩下的下一轮继续。
- 不想等到凌晨就 `SnapLog --ocr-pending`，或托盘菜单“批量识别待识别记录…”。

## 截图逻辑

窗口切换驱动的抓取是这样的：

```
某个窗口第一次出现 → 等“延时截图时长”（默认 5 秒，让页面渲染出内容）
                        │
                        ├─ 期间又切窗口了 → 重新计时
                        │
                        └─ 等满后前台还是这个窗口 → 截图并识别
```

**同一个窗口在一个“抓取周期”（默认 10 分钟）内只记一次。** 一个周期内反复切回去不会重复记，过了一个周期再打开才重新记一条。

这样做的原因：

- **延时是为了避开半渲染的页面**。刚切过去的窗口经常还是白屏或骨架屏，立刻截图只能得到没有信息的画面。5 秒足够大部分页面渲染出内容。
- **"等满后还是这个窗口"是双保险**。延时期间用户切走了，那次等待会被取消；就算延时刚结束用户又切走了，也会再核对一次当前前台窗口，不是它就放弃这次抓取。
- **周期内去重是为了避免刷屏**。窗口标题随时在变（浏览器标签、文档名），如果每次切回去都记一条，一个上午能攒出几千条几乎相同的内容。按"进程 + 窗口类名 + 标题"识别是不是同一个窗口。

想更灵敏就把“延时截图时长”和“抓取周期”调小；想更省就调大。抓取只由窗口切换驱动，没有定时轮询——同一个窗口在一个周期内不会重复记录。

## 记录、截图与保留策略

### 每条记录都带截图

默认**开启**保存截图，所以每条记录都能对应到当时的画面。文件名精确到毫秒，同一秒被手动和定时各抓一次也不会互相覆盖。截图目录可配（支持环境变量），库里存**绝对路径**（旧版本的相对路径也照样能打开）。

记录里除窗口标题外还采集**窗口类名**（`Chrome_WidgetWin_1` 这种）。类名比标题稳定，用来区分窗口类型——比如同一进程下的弹窗和主窗口。

### 保留策略

| 配置项 | 默认 | 作用 |
|---|---|---|
| `Capture.ImageRetentionDays` | 30 | 超过就从磁盘删掉截图文件 |
| `Storage.RecordRetentionDays` | 0（永久） | 超过就从数据库删掉记录 |

清理时机：程序启动时、托盘应用每天一次、以及手动 `SnapLog --cleanup`（会**如实报告删了什么**）：

```
[结果] 删除 2 条过期记录；删除 2 张过期截图（释放 4 B）
```

截图被删后，对应记录的截图路径会被**清空**（而不是留一个指向不存在文件的路径），所以记录查看器里"有没有截图"永远是真的。

> 用“每天定时识别”时注意：截图保留天数要大于批次间隔（按天算，正常远大于）。万一截图先被清掉，批次会把那条记成 Error 并注明"截图文件不存在"，不会静默丢。

## 接入大模型总结

**默认关闭，且默认不会发起任何网络请求。**

### 1. 配密钥（推荐环境变量）

```cmd
setx SNAPLOG_OPENAI_API_KEY "sk-你的密钥"
```

环境变量优先于配置里的明文。**不要把密钥写进代码或提交到仓库。**

### 2. 配置模型列表

可配多个，**按顺序使用：前一个重试用尽仍失败就自动换下一个**。同一列表里每个模型可以读不同的环境变量，所以不同网关可以用不同密钥。配置完点“**测试连接**”立刻验证。

| 服务 | Endpoint | Model 示例 |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` / `qwen-vl-max`（带视觉） |
| Moonshot | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |

只填域名会被自动补 `/v1`，预览里显示的是**补齐后实际会被请求的地址**。

### 3. 选择发送内容

| 模式 | 发什么 | 适用 |
|---|---|---|
| **只发 OCR 文字**（默认） | 窗口标题 + OCR 文字 | 最省 token，隐私面最小 |
| **文字 + 截图** | 上面这些，再附上采样后的截图 | 最准：截图能纠正 OCR 错字、补上漏掉的内容 |
| **只发截图** | 只有截图，不带 OCR 文字 | OCR 效果差的界面。需要视觉模型，token 更贵 |

**同窗口图片采样**：同一个窗口在“同窗口图片最小间隔”（默认 300 秒）内的多张截图只挑一张。一个窗口停着不动半小时、被定时抓了 6 次，只会发 1 张。再受“最多附带张数”（默认 6）兜住成本上限。实测：3 条同窗口、间隔 7~9 秒的记录，在 300 秒采样间隔下只挑出 **1 张**。

图片统一转成 JPEG（质量 85）：全屏 PNG 150KB+ → 约 100KB，而视觉模型不需要无损。

### 4. 失败重试

| 配置项 | 默认 | 说明 |
|---|---|---|
| `RetryCount` | 2 | 单个模型内部的重试次数（不含首次） |
| `RetryDelaySeconds` | 3 | 第一次重试等这么久，之后 2 倍递增（3→6→12 秒），上限 60 秒 |
| `RequestTimeoutSeconds` | 120 | 单次请求超时，超时也计入重试 |

**只重试"等一等可能就好"的错误**：超时、429、5xx、以及拿不到任何 HTTP 响应（DNS 失败、连接被拒、TLS 失败）。401/400/404 这类事实性问题不重试，直接跳到下一个模型。

失败时列出**每个模型的每次尝试**：

```
[结果] 生成失败：所有模型都没能完成请求（共尝试 4 次）。
  · 甲模型 · m-a @ 127.0.0.1 第 1 次：接口返回 0：由于目标计算机积极拒绝，无法连接。 (127.0.0.1:9)
  · 甲模型 · m-a @ 127.0.0.1 第 2 次：接口返回 0：由于目标计算机积极拒绝，无法连接。 (127.0.0.1:9)
  · 乙模型 · m-b @ 127.0.0.1 第 1 次：接口返回 0：由于目标计算机积极拒绝，无法连接。 (127.0.0.1:9)
```

> 程序**关掉了 SDK 自带的重试**（`RetryPolicy = new ClientRetryPolicy(0)`），重试策略统一由配置决定。否则两层重试相乘（配置 2 次 × SDK 4 次 = 单请求最多 8 次）——实测踩到过：配置写"重试 1 次"却因为 SDK 内部重试跑了 17 秒。

### 5. 发送前先看清

“预览将发送的内容”或 `SnapLog --summarize --preview` 会打印：会尝试哪几个模型、哪些缺密钥、发送内容模式与文字字数、**会附带哪几张截图**（时间点、进程、窗口标题、路径，但不贴 base64）、完整提示词。

预览**不需要密钥就绪**——你正是要先看清"会发什么"才决定配不配密钥。

2. 匹配不上的活动统一归到 `其他`，不要硬塞进不相干的项目。

### 系统提示词

（以前是“留空就用内置模板”，配置里存在两种状态；现在首次加载时会把默认模板直接填进去，界面上显示的、改的就是它。

## 定时任务

三个"每天到点跑一次"的任务，共用一套调度：

| 任务 | 配置项 | 默认时间 |
|---|---|---|
| 批量文字识别 | `Ocr.Mode = ScheduledBatch` + `Ocr.BatchTimeOfDay` | 02:00 |
| 定时生成总结 | `Summarization.ScheduleEnabled` + `ScheduleTimeOfDay` | 18:30（**按天补生成**，见下）|
| 定时写入总结到飞书 | `Feishu.Enabled` + `Feishu.ScheduleTimeOfDay` | 19:00 |

调度器的几个刻意设计：

- **一天只跑一次**，而且"跑过了"记在状态文件里，**重启程序不会重跑**（否则电脑一天重启三次就总结三次、推送三次）。
- **定时总结按天补生成**：每条总结对应一整天，规则只有两条——
  **① 还没生成过的天**（在有记录的前提下）补生成；
  **② 已经生成过、但那天的数据在那之后又变了**的天，重新生成并**覆盖**旧的那份
  （同一天只保留最新一份：旧记录会被删掉，旧文件一并清理）。"变了"包括新增了记录，
  也包括已有记录的文字被后补上（见下）。
  每次最多补 3 天、最多往前看 7 天（避免某天突然补几十天、一次花掉大量模型调用）。
  判定依据是总结记录里的 `covered_day`（覆盖哪一天）、`covered_marks`（生成当天最大记录 id）与
  `covered_text_rev`（生成当天最后一次记录改动时间）。后者用来认**文字后补**：
  定时批量识别把当时没识别的截图补上文字时，记录条数和 id 都不变，只有改动时间会变——
  那种情况同样要重新生成并覆盖。
  当天不参与——还没过完；手动生成可以在总结记录页勾“只总结指定日期”，只汇总某一天。
- **错过就补跑**：设定时间在程序启动之前（定了 02:00，早上 9 点才开机），启动后第一次检查就会跑。
- 三个任务互不影响，一个失败不影响另一个；跑完弹托盘提示（**失败也会弹**）。
- 每 30 秒重新读一次配置，改完不用重启。
- `--diagnose` 会显示每个任务的下次执行时间，例如 `批量文字识别　待补跑（设定 02:00 已过）`。

## 写入飞书多维表格

把**大模型生成的总结**写进飞书多维表格（Bitable），便于在手机上回看、或者接飞书的仪表盘/自动化做统计。**一条总结写表里的一行**。

整条链路分三层，实现和使用都绕不开这三层：

```
① 数据层：飞书多维表格（app_token + table_id）
        ↑ 写入
② 通道层：自建应用凭证 → tenant_access_token → 多维表格开放接口
        ↑ 调用
③ 触发层：生成总结后自动 / 定时任务 / 托盘菜单手动 / 命令行
```

### 什么时候写、写哪几条

| 触发方式 | 配置 | 说明 |
|---|---|---|
| 生成总结后立即写入 | `Feishu.PushAfterSummary` | 每次成功生成总结就把它写进表里。配合“定时生成总结”= 每天自动汇总 |
| 定时写入 | `Feishu.Enabled` + `Feishu.ScheduleTimeOfDay` | 到点把还没写入的总结写进表（每天只跑一次） |
| 手动 | 托盘菜单“把总结写入飞书表格…”/ 设置页“立即写入…” | 点之前会告诉你有几条待写入 |

写入范围由 `Feishu.PushLookbackDays` 控制：默认 **1**（只写当天生成的），避免第一次开启时把历史总结一股脑导进表里；要补历史就把它调大。

**去重**：写成功的总结会在库里打上 `pushed_at` 标记（“总结记录”页有一列“飞书”能看到），所以重复点“立即写入”不会在表里刷出重复行。写失败的保持未标记，下次重试不会漏。只写**成功生成且有正文**的总结——失败的运行没有内容可导。

### 配置（5 项）

| # | 配置项 | 说明 |
|---|---|---|
| 1 | **App ID** | 开发者后台里自建应用的 App ID，形如 `cli_xxxxxxxxxxxxx` |
| 2 | **App Secret** | 建议放环境变量：`setx SNAPLOG_FEISHU_APP_SECRET "你的密钥"`。**不要写进配置文件或提交到仓库** |
| 3 | **app_token** | 整张多维表格的标识。从 URL 里取：`https://xxx.feishu.cn/base/xxxxxxxxxxxxxxxxxxxxxxxx` → `xxxxxxxxxxxxxxxxxxxxxxxx`。同一张多维表格下的多张表共用 |
| 4 | **table_id** | 每张数据表各有一个，形如 `tblxxxxxxxxxxxxxx`。换表或新建表后要重新获取 |
| 5 | **字段映射** | 总结字段 → 飞书表里的列名。默认 5 条（时间/触发来源/模型/记录条数/总结），**可以增删**；表里没有对应列的映射把“飞书字段名”留空即可跳过，不必每条都填 |

接口基址 `https://open.feishu.cn/open-apis`。

### 字段映射怎么改

- 设置页“推送配置 → 字段映射”：**新增… / 编辑… / 删除 / 恢复默认**。编辑时“总结字段”是下拉（带中文说明），“飞书字段名”也是下拉。
- 点**“读取表字段名”**会只读一次表结构，把**真实列名**填进下拉（显示成 `列名（类型）`），并按你当前映射列出哪些列名在表里找不到。手打列名容易差一个空格，建议先点这个。
- 可映射的总结字段：`StartedAt` 总结生成时间、`FinishedAt` 完成时间、`Trigger` 触发来源（手动/定时/命令行）、`Provider` 模型、`RecordCount` 记录条数、`ImageCount` 截图张数、`ElapsedMilliseconds` 耗时(毫秒)、`Attempts` 尝试次数、`Markdown` 总结正文（字段名沿用，内容为纯文本）、`Preview` 总结摘要(前120字)、`SavedPath` 本地文件路径、`Message` 结果说明。
- 从旧版本升级：以前推的是抓取记录，配置里的字段映射（时间/进程/窗口标题/识别文字…）在总结上取不到值，程序会自动换成总结字段的默认映射，并在推送配置页用红字提示你重新核对列名。

### 三个踩过坑的点，程序里都处理了

**1. 鉴权用应用身份，令牌缓存复用**

调 `POST /open-apis/auth/v3/tenant_access_token/internal`，用 App ID + App Secret 换 `tenant_access_token`，有效期 7200 秒。程序**缓存令牌并提前 5 分钟刷新**，不会每写一条就换一次令牌。同一个进程里多个写入器共用一份缓存。

**2. 权限要两层同时满足**

| 缺哪一层 | 飞书报错 | 怎么办 |
|---|---|---|
| API 权限范围 | `99991672` | 开发者后台给应用开通多维表格读写权限（`bitable:app`） |
| 文档级协作授权 | `91403 Forbidden` | 把这个应用**加为这张多维表格的可编辑协作者**（只开 API 权限不够） |

这两个码程序会翻译成人话直接告诉你缺哪一层——不用去猜。

**3. 写入前先核对字段名**

飞书按字段名**精确匹配**，差一个空格、一个换行都会报 `1254045 FieldNameNotFound`。所以程序在写入前先调一次“列出字段”，把映射里的名字和表里实际列名核对一遍：对不上就在**写入之前**直接告诉你是哪一列，而不是写一条报一次错。映射里一条飞书列名都没填时也会直接拦下，不会写出一堆空行。

### 其他行为

- **测试连接**按钮 / `SnapLog --publish --test`：换一次令牌 + 列出字段 + 核对映射，**不写入任何数据**。这一步能一次性验证权限两层是否都配好、字段名对不对。
- **读取表字段名**按钮：只读表结构（`fields` 接口），同样不写任何数据。
- `SnapLog --publish --dry-run`：只列目标表格、字段映射、待写入的总结清单，不发任何请求（也不需要密钥）。
- 按类型自动转换值：日期列发毫秒时间戳、数字列发数字、复选框发布尔、其余发文本。所以飞书那边可以把“时间”建成日期列、“记录条数”建成数字列。
- 分批写入（默认每批 200 条，单次最多 200 条总结），部分批次失败会如实报告写了多少、失败了哪些批。
- 总结正文超长会截断并标注（默认上限 2000 字，`Feishu.MaxTextLength`）。
- 失败时保留飞书返回的原始信息，例如 `换取令牌失败：App Secret 不正确 —— app secret invalid`。

> ⚠️ 总结正文（可能包含屏幕上识别出的内容）会上传到飞书。请确认这张表只有你（或你信任的人）能看。发送前界面会再确认一次。

## 数据放在哪

```
%LOCALAPPDATA%\SnapLog\
├── activity.db               记录本体（SQLite，WAL 模式）
├── activity.db-wal           写入日志（正常退出时合并回主库）
├── state.json                程序运行状态（界面标记、定时任务上次执行时间）
├── summaries\                生成的总结（纯文本 .txt）
├── images\                   截图（目录可改，见 Capture.ImageDirectory）
├── logs\                     按天滚动的运行日志
└── appsettings.json          只有在界面点“保存设置”时才会生成
```

程序目录下另有 PaddleOCR 运行时：`paddle_inference.dll`(94MB)、`mklml.dll`(93MB)、`opencv_world470.dll`(64MB)、`paddle_yt_phi.dll`(46MB)、`PaddleOCR.dll` 和 `inference\` 下的模型。

配置查找顺序：`--config` 指定 → `%LOCALAPPDATA%\SnapLog\appsettings.json` → 程序目录下随发布附带的那份。

> **为什么程序状态单独放一个文件**：用户目录里的配置会覆盖随程序发布的默认值。早期版本为了记住"首次运行提示看过了"会把整份配置快照写进用户目录，结果以后每次升级改默认值都被这份旧快照挡住（开发过程中被坑了两次：换了 OCR 引擎却发现没生效）。现在程序只写 `state.json`，`appsettings.json` 只在用户点“保存设置”时才写。

### 数据表

**`activity`**：`id` / `timestamp`（TEXT，精度到秒）/ `process` / `title` / `window_class` / `text` / `ocr_ms` / `capture_method` / `image_width` / `image_height` / `image_path` / `status`（`Ok` / `NoText` / `Error` / `Pending`）/ `error`。

**`summary_runs`**：`id` / `started_at` / `finished_at` / `trigger` / `success` / `provider` / `attempts` / `markdown` / `saved_path` / `message` / `record_count` / `image_count` / `elapsed_ms`。

索引：`activity(timestamp DESC)`、`activity(process)`、`activity(status)`、`summary_runs(started_at DESC)`。时间戳存成文本，字典序即时间序：

```sql
SELECT timestamp, process, window_class, title FROM activity
WHERE timestamp >= '2026-09-30 09:00:00' AND status = 'Ok'
ORDER BY timestamp DESC LIMIT 20;
```

**schema 会自动迁移**：老库没有 `window_class` 列，打开时用 `PRAGMA table_info` 检查并 `ALTER TABLE` 补上，历史记录一条不丢（实测在 18 条记录的真实旧库上验证过）。

### 迁移

- 旧版 `activity.csv`：库为空时首次启动自动导入（LF/CRLF 都能读），**不删除原文件**。
- 旧版单模型配置（`Summarization.Endpoint`/`Model`/`ApiKey`）：自动合成一条“迁移自旧版配置”进模型列表。
- 旧版 `ShowFirstRunNotice` 键：被忽略，不报错。

## 隐私与安全

这个工具会持续记录屏幕文字**和截图**，请明确：

- **默认不联网。** 只有你主动点“生成总结”/“立即写入”并确认后才发到配置的接口；定时任务和“生成后自动写入”都需要你显式打开对应开关。总结的隐私确认记在 `Summarization.ConsentGranted`。
- **截图默认存本机磁盘**，包含屏幕上的一切。想少留：调小“截图保留天数”，或关掉“保存截图文件”（但那样就不能用定时识别了）。
- **带图模式会把截图原图上传**，画面里的所有内容都会被发出去。命令行用 `--summarize` 时若配的是带图模式，确认提示会额外警告。
- **写入飞书会把总结正文上传到飞书多维表格**（可能包含屏幕上识别出的内容）。发送前会先告诉你这一次要写几条、写到哪张表。
- **发送前可以预览**：命令行 `--summarize --preview` 能看到会附带哪几张截图和完整提示词。**预览不联网。**（界面上的预览按钮已移除；每次真正生成前仍会弹一次外发确认，写明接口与模型。）
- **OCR 模型随程序离线运行**，不会联网下载模型。
- **建议把敏感应用加入排除列表**（`Triggers.ExcludedProcesses`）。`run.cmd --windows` 能看到进程名。
- **窗口标题也会被记录**，浏览器标题可能包含文档名。
- **不要提交配置文件里的密钥/令牌**；`.gitignore` 已忽略本地私有配置。
- 抓取是**只读**的：不注入、不修改任何窗口。程序以 `asInvoker` 普通权限运行，不要求管理员。

## 资源占用与实测数据

Windows 10 21H1 / .NET 10.0.12 / 12 逻辑核心。

| 项目 | 实测值 |
|---|---|
| OCR：系统内置（1650×925） | 232 ~ 490 ms，进程内存约 56 MB |
| OCR：PaddleOCR v6 tiny，MKLDNN 关 | 全屏约 4~6 s，稳定态约 145 MB |
| OCR：PaddleOCR v6 tiny，MKLDNN 开 | 全屏约 1.4 s，稳定态约 643 MB |
| 真实 WinForms 进程峰值（单次抓取，MKLDNN 关） | 281 MB |
| 批量识别 3 条（定时模式补识别） | 18.7 秒（约 6.2 秒/条） |
| 程序目录 | 约 460 MB |
| 自包含发布 | 约 600 MB |
| 空闲 CPU | 0 轮询，只有窗口事件回调 |

省资源的做法：

- **窗口监听用系统事件钩子而不是轮询**，空闲时没有定时器在跑。
- **OCR 延迟加载**，不用就不付 100MB 和 400ms。
- **可以把识别挪到每天空闲时段**（定时批量模式），白天只截图。
- **默认关掉 MKLDNN**，用时间换 500MB 内存。
- **截图、OCR、写库全部在后台线程 `async`**；原生推理是同步调用，被显式丢到线程池。
- **SQLite 单条长连接 + 信号量串行**；WAL 让写入不阻塞读取；INSERT 只预编译一次。
- **列表查询只取摘要**，完整文字按需按 id 单取。
- **保留策略**自动清掉过期截图与记录；日志按天滚动并清理超期文件。

### 本机上实际验证过的

- **OCR 准确率正面对比**：同一张真实截图、同一套 24 个词组，系统 OCR 9/24、PaddleOCR 22/24。
- **MKLDNN 权衡**：开/关各跑一遍，准确率一致（22/24）而内存差 500MB。
- **内存回收**：加载 → 识别 → Dispose 逐阶段测量，得出"能回收多少、不能回收多少"。
- **原生噪声屏蔽**：对照组（不静音）banner 两次，实验组（静音）0 次，且 .NET 自身输出不受影响。
- **免费版 100 框限制**：合成图 99 行成功、101 行失败；真实截图整图失败、2×2 分块成功。
- **定时批量识别全链路**：3 条记录以 `Pending` 落库（只截图不识别，状态栏显示"等定时识别"）→ `--diagnose` 报"待识别 3 条"和"待补跑" → `--ocr-pending` 识别 3 条成功 → 文字回写、待识别归零。
- **三种传参模式**：`--summarize --preview` 逐一验证——只文字 3108 字符无图；文字+图 1 张图；只发图时不含 OCR 文字。
- **图片采样**：3 条同窗口、间隔 7~9 秒的记录，300 秒采样间隔下只挑出 1 张。
- **多模型回退与重试**：两个不可达地址、各重试 1 次 → 共 4 次尝试、10 秒，失败清单逐个列出。
- **工作项目清单进入提示词**：预览里能看到 3 条项目与归类要求。
- **系统提示词覆盖**：填了自定义内容后，system 提示词完全替换，且项目清单仍自动附上。
- **总结历史记录失败**：用不可达地址跑一次，历史表里落了一条 `trigger=命令行 / success=0 / attempts=1 / 耗时 2168ms` 并带完整失败原因。
- **待写入清单**：`--publish --dry-run` 正确列出库里的待写入总结（条数、时间、触发来源、摘要）与字段映射，并提示不会发起任何写入。
- **写入去重**：待写入查询/标记语句在临时库上验证——只取“成功 + 有正文 + 未标记 + 在范围内”的总结；只标记写成功的那几条，未成功的保持待写入。
- **飞书鉴权链路对真实 API 验证过**：用真实 App ID + 假 secret 请求鉴权接口，飞书回 `10014 app secret invalid` —— 说明端点地址、请求体字段名（`app_id`/`app_secret`）、响应解析全部正确；换成 App ID 格式不对则回 `10003 invalid param`。
- **飞书三个接口路径对真实 API 验证过**：`fields`（列字段）和 `records/batch_create`（批量写入）不带令牌请求都返回 400（缺鉴权），而故意写错的路径返回 404 —— 说明路径构造正确。
- **保留策略**：造 2 条 2020 年记录 + 2 张旧截图，`--cleanup` 正确删除并保留今天的。
- **schema 迁移**：在 18 条记录的真实旧库上验证，列被补上且数据不丢。
- **界面自检**：五个配置页（抓取 50 / OCR 29 / 大模型 74 / 推送 38 / 关于 28 个控件）+ RecordsForm + MainForm 全部构造/加载/关闭无异常。
- **截图逻辑**：真实切换一次前台窗口，走通了“切换 → 延时 → 核对仍是该窗口 → 抓取”整条链路；延时期间切走时正确输出“延时结束但前台已经不是刚才那个窗口，跳过本次抓取”。
- **设置页性能**：改之前主窗口构造 290ms（4 个标签页一次性全建）；改成设置页懒加载 + 空闲预建后 **25~31ms**，设置面板本身在空闲时预建（约 200ms，用户感知不到），托盘菜单的设置弹窗也改成复用而不是每次新建。
- **完整链路**（`--selftest`）：抓取 → 分块 OCR → 截图落盘 → 库往返文字完全一致 → 筛选/分页 → CSV 导出校验通过。

实测中修掉的几个真实缺陷：PaddleOCR 原生依赖因 `exclude="Build,Analyzers"` 不被复制；原生库污染 stdout 导致 CLI 输出编码错乱；SDK 自带重试与本程序重试相乘；连接失败被包成 `AggregateException` / `ClientResultException(0)` 导致重试判定失效；CSV 读取按 CRLF 匹配行终止符导致 LF 文件一条都读不出来；`WindowsFormsSynchronizationContext` 装上后没有消息循环泵导致界面自检死锁；UI 状态写入用户配置导致升级后新默认值被旧快照挡住。

## 已知限制

### 稳定性：一次"GDI+ 泛型错误"的定位与修复

有用户遇到过程序弹出一个"SnapLog 遇到未处理的错误：ExternalException: A generic error occurred in GDI+"的对话框。定位与处理：

- **这不是崩溃**：它是 UI 线程上一个可恢复的异常，被我的全局处理器当致命错误弹了模态框。程序其实还在跑。
- **根因是跨线程碰 UI**：引擎的抓取事件在后台线程触发，而托盘代码在那个线程上直接改了 `NotifyIcon.Text`。`NotifyIcon` 背后持有一个 GDI+ 图标和一个消息窗口，后台线程碰它，撞上 UI 线程正在进行的图标操作，就会抛 GDI+ 泛型错误。已修：所有 UI 操作先切回 UI 线程。
- **压测与复现**：纯截图 400 次零失败、内存平坦；开着 OCR 快速切换窗口 477 次、跑 90 秒，没崩、没异常。这个竞态本身没法稳定复现，所以我把它改成"可恢复 + 带栈记录"，而不是假装修好了。
- **顺带修了**：取消被误当成"写入 CSV 失败"记日志（取消本来就不是失败）；`FileLogger` 现在带完整栈，下次再出这种事能直接定位。

涉及这一类的行为都收紧了：
- 抓取路径加了总兜底：任何环节失败都只是"跳过这一次"，不会往上抛。
- 菜单的异步处理器统一包了一层 Guarded：里面炸掉也只弹个托盘气泡。
- UI 线程异常不再弹崩溃框，改成托盘气泡 + 记日志，程序继续跑。
- 只有真正没人接住的非 UI 线程异常（进程已经保不住）才会弹窗并退出。



1. **只有 x64。** PaddleOCR 原生推理库只有 win-x64 版本。
2. **免费社区版限制单次调用文本框数 < 100。** 已用自适应分块绕过，代价是密集页面耗时成倍增加；极端密集内容会有区域被跳过，此时会在日志和记录的“错误”列里明确写出来。
3. **PaddleOCR 慢于系统 OCR。** 默认配置下一张全屏约 4~6 秒。用定时批量识别可以避开这个矛盾。
4. **飞书写入已端到端跑通。** 最初只验证到"权限与字段名都配好了"（真正落一行没验过），后来一次真实写入成功——库里那条总结被打了 `pushed_at` 标记，而这个标记只在飞书返回 `code=0` 之后才写。鉴权、权限两层、字段核对、批量写入、去重标记这条链路整体是通的。
5. **升级后要核对一次字段映射**：以前推的是抓取记录，映射里的字段名（Timestamp、OcrText…）现在没有对应值，程序会自动换成总结字段的默认映射并在推送配置页红字提示；默认列名（时间/触发来源/模型/记录条数/总结）大概率和你表里的列名不同，点“读取表字段名”再从下拉里选一次即可。
6. **带图模式需要模型有视觉能力**，且按图计费。用 `MaxImages` 和 `ImageSampleSeconds` 控制成本。
7. **定时任务"错过就补跑"**：如果关机一整天，开机后三个任务会各补跑一次。这是刻意设计（每日任务语义），但意味着开机后可能立刻有一次 OCR + 一次模型调用 + 一次推送。
8. **原生内存不完全可回收**：约 90MB 要等进程退出。空闲卸载实测只省 38MB，因此未实现。
9. **分块识别的阅读顺序是恢复出来的**：按文本块坐标重排合并，极端版面（多列、表格）下顺序可能不完美。
10. **保留策略按时间删，不做内容分析**：调小天数就是真的删掉，没有回收站。要归档请先导出 CSV 或配飞书推送。
11. **关键词搜索走 `LIKE`，不是全文索引。** 这个量级够快；要积累到几百万条并频繁全文搜索可自行加 FTS5。
12. **时间戳精度只到秒**，毫秒会被丢掉。
13. **最小化的窗口抓不到**（会明确跳过并记录原因）。
14. **受保护内容抓不到。** DRM 画面、部分硬件加速窗口 `PrintWindow` 返回纯黑；程序检测到"纯色画面"会自动降级到下一级策略。
15. **以管理员运行的窗口**可能读不到进程名（留空），标题和画面一般仍可抓。
16. **系统 OCR 备用引擎需要中文语言包**，否则中文识别成乱码。

## 扩展点

**换 OCR 引擎。** 实现 `IOcrEngine`，在 `OcrEngineKind` 加枚举值，在 `OcrEngineFactory.Create` 加分支。
